# Repository Guidelines

## Project Overview

Tern Plotroom is a [Tern](https://tern.sh) terminal plugin, written in Luau, that renders one block, shown as Plotroom, for a live queue of GitHub pull requests, GitHub issues and Jira issues: one sidebar of typed saved views, keyboard triage, Browser docking, and one-key worktrees. The block's identity stays `plugin.plotroom.prs` (manifest block id `prs`) so existing PR panes restore. Data comes from the `gh` CLI (GraphQL), Atlassian's `acli` (Jira) and `git`; there is no server component.

There is one block. `Plotroom: Open` (id `open`) is its one entry point; the other palette commands (`flows.COMMANDS` plus `open-selected`, `worktree-selected`, `goto-selected`, `agent-selected`) act on the focused Plotroom block, except `Open item by URL`, which launches one when none exists. The old `plugin.plotroom.issues` block and its `open-issues` command are removed; Tern has no pane migration hook, so an old Issues pane must be reopened through Plotroom (saved views and prompts are not touched, and nothing is migrated). The `KINDS` table (`prs`, `issues`) in `host.luau` replaces the old block-wide `Kind`: each kind fixes its label, icon (`merge`, `list-checks`; a name outside Tern's icon set draws blank), kv keys, allowed integrations, seed views, `?` list and prompt variables, and each saved `View` (`{id, kind, name, integration, query, logins, group, prompts}`) carries its own `kind`, so the details, actions and wording follow the active view (`State.kind` is only the active view's). In memory a view's id is `prs:<kv id>` or `issues:<kv id>` (the pinned PR's is `pin`); the stores stay kv `views-prs`/`views-issues` and `prompts-prs`/`prompts-issues`. `orderedViews` lists views in the sidebar grouped by integration and login, GitHub pull request and issue views together, Jira views alongside. Settings › Views lists, while gh is on, a group per signed-in gh login (`ghActive.accounts`; the page reads them even with no GitHub view) and, while acli is on, Jira's, plus any other group a listed view sits under (a signed-out login, several logins). An account's or Jira's group ends in an Add view button (`vadd:github:<login>`, `vadd:jira:`): a view of that integration and explicit login, of `State.kind` where the integration allows it, else an issue view. A view's integration and logins never change in Settings (no Integration or logins row). Its Type row (`vkind`, GitHub views only) writes the view into the other kind's store under a new id (destination first, so a failure leaves the original), keeping name, query, logins and group-by while it still holds, and resets the prompts offered. Saved prompts are called **actions** wherever the user reads them (Settings › Actions, Add action, All actions…); code, row ids (`popen:`, `padd:`), the page id `prompts` and kv keys still say prompt. Settings › Actions lists the actions of each kind that has an integration on. `jira.luau` reads Jira through `acli` (kv `jira-repos` maps a project to its repositories); `tracker.luau` holds the tracker-neutral `Issue` type and the name formats (`render`, `formatProblem`, `{github.user}`-style dotted vars); links are `plotroom://issue/...`, rpc op `issue`. Name formats (host table `formats`): new issue branches (kv `branch-format`, per-repo override kv `branch-formats`) and worktree folder names (kv `pr-dir-format`, `issue-dir-format`). An issue worktree is on its one live linked PR's branch (`github.linkedPrs`; several → the window's `choosePr` picker), else a new branch from a base the window's `chooseBase` picker asks for (`worktree.openIssue` answers `UNDECIDED` / `NEED_BASE`). PR worktrees are on the PR's head branch (`worktree.prBranch`; forks `<owner>/<branch>`). Item picker ids are `n<number>` (PRs) or `n<ref>` (issues); the item's actions are `itemActions` (the action bar shows only those with a key; Open is the preview head's globe icon); CSS selectors cover both surfaces.

## Architecture & Data Flow

Two Luau runtimes talk through Tern:

- **Host** (`plugin/host.luau`): runs where the block runs (the remote host's daemon for a remote pane). Owns per-pane `State` (module table `running`, keyed by pane), polls GitHub and Jira, persists prefs in `tern.kv`, returns a declarative `ui.el`/`ui.node` tree from `view`, and does all checkout work (git, gh, omp) and saved-prompt reads for the window. Registered via `tern.block.define("prs", {init, title, view, key, event, save})`.
- **Window** (`plugin/window.luau`): runs on the machine showing the window, so it never touches a checkout. Registers `tern.route.link` for `plotroom://github/<open|worktree|goto|agent|show>/<owner>/<repo>/<n>` and `plotroom://github/run/<owner>/<repo>/<n>/<prompt id>` links (and the `plotroom://issue/...` ones for issues), `plotroom://repos` and `plotroom://jira-projects` (the pickers behind Settings' Add repository and Add Jira project rows, sent back as the block's `add-repo`/`add-jira` actions), `plotroom://confirm` (the palette before a Settings Delete or Remove: it reads the block's hidden `main.confirm` JSON `{row, head, label, detail}`, lists Cancel first, and sends `confirm-delete`/`cancel-delete` with the row, which the host acts on only for the row it asked about), `tern.command` ids (`open`, `open-selected`, `worktree-selected`, `goto-selected`, `agent-selected`, and `flows.COMMANDS`: `open-url`, `agent-go`, `assign-me`, `label-add`, `label-remove`, `jira-transition`, `rerun-failed`, `draft-pr`, `export`, `import`, `mark-seen`, `snooze`, `toggle-snoozed`), reads host nodes by dotted key (the hidden `layer.queue.buttons.<open|worktree|goto|agent|agentgo|prompt-<id>>` links of the selected item's actions, `main.more` (the command palette's link, always shown), the check rows `layer.queue.<required|runs>.run<i>`, and the issue sidebar's linked PR rows under `layer.queue.linked`) via `cx.session:surface`, and only follows a link whose node shows that exact href. Asks the user (pickers, consent) and arranges tabs/agents. `show` (a linked PR row) sends `{ev="action", act="show-pr", value=<PR URL>}` to the block the link came from, never another or a new one; the host selects the PR in the active view when that lists pull requests and has it, else lists it alone in `State.pin` (the sidebar's first scope, a pull request view, so the active kind follows it; fetched by `github.pull`, saved as `pin`) and leaves the other views in the sidebar.
- **Window → host requests** (host section "requests from window.luau", window `ask`/`answered`): window sends `{ev="action", act="rpc", value=JSON{id, op, ...}}` with ops `menu` (saved prompts offered under the active view, each with `worktree`: where it runs, and `split` when its agent opens beside the queue rather than in a tab), `worktree`/`issue` (with `users` when the prompt names `{github.user}`/`{jira.user}`; `worktree` false answers the main checkout, no worktree; `issue` also `pr`/`fresh`/`base` once picked), `where` (an item's noted worktree folder, for Go to tab), `checkout` (verify or clone a repository's checkout), `map-jira` and `jira-projects` (a Jira project's repositories), `repos` (saved repositories and, while gh is on, signed-in gh logins) `profile` (one login's repositories), and the workflow ops: `ctx` (the selected item), `act` (`assign-me`, `label-add`, `label-remove`, `transition` listing then choosing, `rerun-failed`: each answers a plan, never writes), `commit` (runs the plan named by its token, only after the window's confirm), `draft` (`info`, `bases`, `preview`, `plan`), `export-list`, `export` (`preview`, `commit`), `import` (`preview`, `apply`), `open-url` and `worktree-path`; `menu`'s `commands` are metadata objects `{id, group?}` (protocol 18), not bare ids; the host answers in hidden node `main.r<id>` (JSON), renders, then opens `plotroom://rpc/<id>`, which only the asking window acts on. Hidden `main.rpc` holds the protocol version (`RPC_PROTOCOL` in host, `PROTOCOL` in window, now 18); bump both together when the request/answer shapes change, since a remote host may run another Plotroom version.
- **Repositories and checkouts**: views span repositories, so the block has no repository of its own. `init` resolves the launch directory (`launchCwd`) and saves its main checkout under kv `checkouts` (lowercase `owner/name` → path; `""` = listed without a checkout, as Settings › Repositories › Add repository does). Without a checkout, a Worktree, agent or prompt on that repository asks for one through the window's `checkout` op (`claim` verifies a folder or runs `gh repo clone`); per-repository setup commands are kv `setup-commands`, branch formats `branch-formats`. Worktrees always go in omp's worktree directory (`worktree.worktreesDir`: `OMP_WORKTREE_DIR`, else `omp config get worktree.base`, else `~/.omp/wt`); there is no Plotroom setting for it.
- **Integrations follow their CLI** (host table `cli`): the first block of a runtime probes `gh --version` and `acli --version` (`cli.probe`; again on Refresh and on showing a setup page). An integration is on (`cli.on`) only while its CLI starts: `loadAll` lists only views of integrations that are on (their kv stores keep the others), a pin needs the CLI of its item's integration, and `ghActive.note`, the `repos` op, `me.read` and an issue worktree's linked-PR lookup ask gh only while it is on. Until every CLI answered (`cli.ready`) no view is listed or searched and the queue shows loading; the restored active id is kept (`save` writes `State.activeId`), and once the answers are in, or one changes, every block reruns `reloadViews`. A setup page holds one row (`guide:<id>`, `act = "guide"`) whose button opens the CLI's install guide (`cli.list[].url`).
- **Worktree card** (`State.notes`, by item key; the card and the rows' Worktree badge): memory only, but a cache of git, never the source, so a fresh block or one after a plugin reload shows the worktrees that exist. `scanWorktrees` (nested in `blockDef`, asked by every `view`, idempotent) runs `worktree.scan` for each saved checkout of the repositories in the shown snapshot (a Jira issue's: the project's mapped repositories) when that snapshot was not scanned yet (each refresh result, a view switch), after a Worktree attempt (`noteWorktree`), a removal or a saved checkout (`state.scanned = nil`): one `git worktree list` per checkout plus, with a PR's worktree there, one `git config` read; no per-row spawns. `applyScans` reconciles: a listed worktree of a listed item with no ok note gets one, an ok note whose worktree its scanned checkout no longer lists goes, and a failed scan, or one that a note change overtook (`noteSeq`), changes nothing. `inspectSelected` reads `git status` for the selected item only (debounced, once per refresh); `dirty` is nil until then. `NOTE_CAP` bounds only the attempts git has not confirmed.
- **Shared helpers** (no cycles): `host → github, input, jira, keys, process, prompts, tracker, worktree, triage, sorting, portable, board` (the last four as `flow.triage`, `flow.sorting`, `flow.portable`, `flow.board`); `window → flows, worktree` (`flows` takes what window owns through `flows.setup(Env)`, so it requires nothing); `worktree → process, github, tracker`; `jira → process, tracker, github` (`jira.transitions`/`jira.transition` use `tern.fetch` on the acli site's fixed `rest/api/3` routes with `PLOTROOM_JIRA_API_TOKEN` read per call from the host environment and the acli email, after `/myself` names that email; the token is never in kv, argv or a message); `github → process, input, tracker`; `tracker → input`; `process`, `input`, `keys`, `prompts`, `flows`, `triage`, `sorting`, `portable`, `board` have no requires.
  - `flows.luau`: the window's workflow flows. Agent links (kv `agent-links`, newest first, cap 200: `{key, agent, host = {id, name, address}, at}`; a link counts only for the Plotroom block on the same host; a malformed store is never written over) and the ~4 s `tern.timer` that sends `agent-status` (the full map for the block's host) only when it changed, running only while a Plotroom block and a link exist (restarted by `window_start`, `pane_created`, a new link). The guided mutations (`confirmPlan(cx, pane, plan, done)`: Cancel first, then `confirm.label` and the plan's lines, `commit` only after the confirm and with that plan's token), draft PR, export/import, Open item by URL, `plotroom://worktrees/open/<n>` and `COMMANDS` (palette ids window.luau registers, each with a `group`; `keyed` ones the command palette lists as their queue action instead). The command palette itself (`plotroom://more`, window.luau `palette`) asks `menu` with `palette = true` and lists in `GROUPS` order (Saved actions, Jira - Issue, GitHub - PR, GitHub - Issue, Triage, Filter & Sort, Views, Worktree, GitHub, Jira, Configuration; a group the window does not know follows; the typed headings hold the selected item's provider operations, the plain GitHub/Jira ones only unscoped operations): the host's `queue` rows (`flow.paletteActions`: only what applies to the selection now, with their group and key, each sent back as `{act = "queue", value = id}` and run through `flow.queueAction` only when `paletteActions` still offers it; with no item, only the rows that need none: Filter & Sort, Views (each sidebar scope as a `queue` row `scope:<id>`) and Configuration; the host validates the chosen scope against the live scopes through the same dispatcher a key uses), Type a prompt… and the saved actions (each through its `prompt-<id>` link) under Saved actions when an item is selected (Go to agent joins them; there is no Agent picker row), and the non-`keyed` `COMMANDS` the host named as applicable (`comment`, `assign-me`, `label-add`/`label-remove`, `issue-close`/`issue-reopen`, `pr-ready`/`pr-draft`, `jira-transition`, `rerun-failed`/`rerun-all`/`cancel-run`, `draft-pr`, `export`, `import`, `open-url`).
  - `triage.luau`: pure triage memory (kv `triage`): `signature` (FNV of the fields whose change matters; green checks do not count, a flipped check does), `status` (`new` | `changed` | `seen`, snoozed), `markSeen` (the only way an item becomes seen; called by the Mark seen action (`flow.mark`) and by `flow.autoSeen`, run from `view`: the selected item is marked with the data it shows, once per `key\0signature` in `state.seenTried`, never on a background fetch, the Worktrees list; an unreadable store is not written over), `snooze`, `tomorrow` (`os.time` of 08:00 local on the next calendar day, never the same day), `attention` (an agent in `waiting_input`, or unseen/changed and not snoozed; idle, exited and working agents never count). The attention filter keeps the row at `state.cursor` listed though it is now seen, until the selection moves.
  - `sorting.luau`: the sorts a view may save per kind and integration (`choices`, `valid`, `cycle`, stable `apply`).
  - `portable.luau`: pure export/import of views and actions: `build` (accounts become `account-N` slots; the format has no field for checkouts, paths, setup commands or tokens, and an action whose text matches `secretIn`'s few patterns is left out with a note; 60000-byte cap), strict `parse` (100 views and 100 actions at most), `plan` (conflicts `same-name`/`identical`, remaps), `apply` to copies of the stores. The host writes them (`flow.export`, `flow.importPreview`, which refuses more than 150 plan entries before replying, `flow.importApply`). The window shows export counts and notes Cancel-first before copying or writing, and an import preview with remaps and final skip notes; all skipped changes nothing.
  - `board.luau`: model of the Worktrees list (user-facing name; module and `flow.board` keep the board name): rows read from `worktree.inventory` per saved checkout (caps 200 rows, 50 checkouts, 20 cleanup checks per press), `inspect`, `findCandidates` (read-only), `remove` (refuses main, locked, missing and dirty). Changes/Clean is automatic: `flow.boardScan` (from `view` and a timer, only while the board is shown; leaving it stops the scan) reads each row's dirty state, the selected row first, `CAP_SCANS` (40) worktrees per scan rotating through the rest, due again `SCAN_SECONDS` (30) after the last start; a scanned row whose changes could not be read shows **Unknown**, an unscanned one "Reading…".
  - Review-fix behaviors: `keys.load` reserves every saved key first, so a built-in whose default another saved key holds loads unbound (`""`), never stealing the custom binding. The window's `flows.agentSync` re-sends `agent-status` whenever the block's hidden `main.agents` node (`flow.agentSig` of the map it holds) is absent or differs, so a reloaded host is told again. The Settings Type row (`vkind`) keeps the view's `sort` when `sorting.valid` for the new kind, else drops it and toasts "Sort order reset".
  - Safety behaviors: every async mutation captures the concrete gh login at plan time and uses it at commit. `rerun-failed` answers all failed runs for a picker and re-runs exactly the selected run; `rerun-all` and `cancel-run` likewise plan exactly the picked finished or active run; `issue-close`/`issue-reopen`, `pr-ready`/`pr-draft` and `comment` (GitHub or Jira) are plan-then-commit like the rest, naming the item and account. The draft flow asks for the repository first (`info`: all distinct GitHub remotes of the checkout), then `bases` for the chosen one; every phase (`info`, `bases`, `preview`, `plan`, commit) validates the repository; the commit aborts if `needsPush` changed, and Esc in a title/description edit returns to the prior review. Export holds the previewed JSON under a token (`preview`, then `commit`) and replies `copyable` (`#tern.json.encode({json=…}) <= flow.EXPORT_COPY`, 50000, measured on the escaped RPC envelope, not raw bytes; raw cap `portable.LIMIT` 60000). The window offers Copy or Write to a file (exclusive): a commit with no `path` returns `json` for the window to copy (only when copyable), one with a `path` writes the file and returns only the path. `open-url` always adds a pin, even when the item is already listed.
  - `github.luau`: `gh` runner, paged GraphQL `search`, `parsePage`/`normalize`/`classify`, account switching, rate-limit quota, the repository picker's cached `accounts`/`repos` lists.
  - `worktree.luau`: repo resolution (`currentRepository` also finds the main checkout), worktree create/reuse (`M.open`, `M.openIssue` from the saved checkout, folder named by the caller's format), `M.remoteBranches`, removal (`M.remove`, host only, never forced: the worktree card's Remove worktree), `within` (path inside a worktree), `M.scan` (what the card is read from: a checkout's worktrees by item key, each item known by its branches or folder names, `Want`, which host `formats.want` builds from the current formats; read-only) and `M.dirty` (`git status` of one worktree), ref validation. Also the board and draft backend: `M.inventory` (every worktree git lists, annotated from per-branch `plotroomkey`/`plotroompr` git config Plotroom notes at creation; local git only), `inventoryDirty`, `removeEntry` (re-reads git's record, never forced; deletes only a branch Plotroom noted, keeps an unnoted one), `draftPreview` (reads branch, base, commits; writes nothing) and `pushBranch` (never forced; the draft's exact head).
  - `process.luau`: the single process runner `M.run(argv, opts, done)`; recovers PATH via login shell, always calls `done`, never throws.
  - `input.luau`: pure text model, single-line or `multi` (UTF-16 offsets for the SDK).
  - `keys.luau`: the queue's one-key shortcuts (action ids and defaults) and kv `keys` (action id → key, `""` removed; per machine, shared by pull request and issue views): every default is `""` (no key) except the command palette's `more` `.`; a saved action's own key beats `agentgo`..`more` (host `key` handler), and imports never take a reserved key; `load` the effective map and why it could not be read, `save` (fail-closed), `action`/`problem`/`shape` for dispatch and validation. The key handler, `?` lists, keycaps, the action bar and Settings › Keyboard shortcuts (page id `keys`: a `Queue` card of `key:<action>` rows, then a card per kind of `pkey:<kind>:<id>` rows, each saved action's own key, which its Actions form no longer shows) all read it, so nothing else hard-codes a queue key.
  - `prompts.luau`: the default prompts (`M.prs` Review, Quick review (`worktree = false`, read only: runs nothing), Address feedback, Watch; `M.issues` Implement, Fix, Plan, the last `worktree = false`), which `KINDS[kind].prompts` holds and `loadPrompts` returns while the kind's kv store is absent (the first edit saves them); `M.missing` lists the defaults no saved prompt is named like (Settings' Restore defaults, row `prestore:<kind>`, act `restore-prompts`, appends them). Written for omp in Plotroom's worktrees: `gh` as `{github.user}` via `GH_TOKEN=$(gh auth token --user …)`, `acli` for Jira, approvals through omp's `ask` tool. Every `{var}` one names must be one the place it runs fills (the window cases assert no `{` is left); each stays under `PROMPT_CAP`.
- Persistence: `tern.kv` keys `views-prs`, `views-issues` (saved views per kind, `{version, nextId, items}`), `prompts-prs`, `prompts-issues` (absent: `prompts.luau`'s defaults), `checkouts`, `setup-commands`, `jira-repos`, `keys`, `branch-format`, `branch-formats`, `pr-dir-format`, `issue-dir-format` (host, per machine), `agent-recent` (window), `agent-links` (window, per machine: see `flows.luau`), `triage` (host: `{version, items}`, item key → `{seen, snoozeUntil, at}` from `triage.luau`, capped at 2000, oldest unsnoozed dropped first, never written over when malformed). A view's own `sort` (`sorting.luau`: `updated`, `oldest`, `review` for GitHub pull requests, `updated`, `oldest` for GitHub issues, `priority` for Jira; absent = default order) is applied in `filtered`, within groups. Issue lists sort by status category (`tracker.byStatus`: In Progress, To Do, Done); Jira search adds `ORDER BY priority DESC, updated DESC` for order within a category. Store changes fan out to other live blocks via `propagate`. host.luau is at Luau's 200-top-level-local limit: group new helpers into an existing table (`formats`, `me`, `cli`) instead of adding locals.
- Block `save` is version 2 (any other version restores fresh): `launchCwd`, `activeViewId` (the view's id in its own kv store; `pin:<item key>` for a pinned item, an older save's bare `pin` is its one pin), `activeKind` (`issues`; absent means `prs`, which is also what a save from the older PR block reads as), `activeLogin`, `pause`, `pins` (the URLs of every pinned item, `flow.pinUrls`: pull request, GitHub issue or Jira issue; `pinView` rebuilds each, so a restored pane refetches and shows them again). An older save's single `pin` URL is still read and added as one pin. Pins live in the sidebar's **Pins** group, capped at `flow.PIN_CAP` (20; a further one is refused with a toast, never dropped), unpinned one by one (`flow.unpin`, the preview's Unpin row or the palette), and have no sort. A view with items selects its first (the Worktrees list, its first worktree); there is no close-preview action, and Esc clears a search or leaves sidebar focus, never the selection.
- Settings multi-line text: Tern 0.8.3 `prefs` has no multi-line control, so a prompt's text is an `editor` node inside a `col` child with `role = "omp.prefs.editor"`, which `prefs` draws as a card over the page; keys still reach the block's `key` handler.
- Settings pages (`PAGE_DEFS`, Tab order, as `cli.pages` shows them): Views, Actions (id `prompts`), Keyboard shortcuts (id `keys`), Worktrees (name formats), Repositories (checkout, own branch format, setup commands), Jira projects (while acli is on), Refresh (id `connection`), then a Setup group with GitHub (`setup-github`) and Jira (`setup-jira`) while that CLI is known not to start; Settings reopens on the page last shown (`State.settingsPage`; Views when that page is not shown now). The sheet's tabs are icons only: plotroom.css hides each tab's `.lbl`, which Tern 0.8.4 leaves showing as "…". `pageContent` builds cards with its local `section`/`row`: Views a card per group (`group:<lowercased label>`), Actions a card per kind, Repositories (`repos`) and Jira projects (`projects`) one card each, of collapsed summary rows (`vopen:`, `popen:`, `ropen:<repo>`, `jopen:<key>`) with a data `hint` and Edit. `Settings.open` names the one expanded item (a view's or prompt's kind-qualified id, a repository, a project key; `openSettings` with a row opens that row's item); its form is its own card `form:<id>` (first in its group or kind, it takes over that card and its title) whose first row is its summary row, Edit turned Done, and Edit focuses its first field. Every form's Delete or Remove row (`delete:`, `pdelete:`, `rremove:`, `jremove:`) comes right after its summary row, and plotroom.css lifts its button onto the summary row, left of Done; its label is hidden, so a failed delete or remove warns on the summary row. Pages have no lead and rows carry their meaning in the label: a `hint` only shows data (a collapsed item's details, a prompt's first line, a name format's variables, the refresh pace) or what a captured shortcut row takes. An Add button is a section of its own whose id starts `add` holding action rows with an empty label (Add, and on Actions Restore defaults while a default is missing), which plotroom.css draws as bare buttons on one line: `add:<…>` under its list, `add-to:<…>` titled with an empty group's or kind's label (prefs skips a section without rows). Delete and Remove rows set `Settings.confirm` and open `plotroom://confirm` (window.luau's palette); there is no Settings overlay. Controls: `choice` for one-of rows (`style = "segmented"`: Enter switches to the next option, as segments draw no keyboard highlight; `style = "menu"`: Enter opens `pick`, arrows move, Enter picks; hover sends `select` `"<row>=<value>"`), `multi` chips; `setValue` takes every `change` (string for a choice, array for chips). Text rows: `props.editing` shows the text edit over any `pick`, so a click on another row or button (the prefs event handler) first ends the single-line edit: it saves, a refused draft keeps the row open with its warning, an empty one is dropped; a click inside the edited field keeps the draft. Shortcut rows (`key:`, `pkey:`) capture the next key: no typing, Backspace removes, Esc keeps (a click elsewhere keeps too).

## Key Directories

- `plugin/` — the plugin (`plugin.toml` manifest, `*.luau` modules, `plotroom.css`). Everything shipped lives here.
- `plugin/tests/` — `regression.luau` (fake-SDK suite + bench), `check.luau` (pure assert selftest, also runnable in-app), `runtime.luau` (smoke driver against real Tern/git).
- `scripts/` — `check.py` (the verification gate) and `tern-0.8.3.d.luau` (pinned SDK type snapshot, sha256-checked).
- `.github/workflows/check.yml` — CI; `.omp/plans/` — historical design plans (README supersedes them).

## Development Commands

```sh
tern plugin link ./plugin          # install for local use
python3 scripts/check.py tools     # download pinned luau 0.742 + luau-lsp 1.70.1 (macOS / Linux x86_64)
python3 scripts/check.py           # all: test + types + bench + smoke
python3 scripts/check.py test      # regression suite only (also: types | bench | smoke)
python3 scripts/check.py --ci      # what CI runs: smoke reported NOT RUN
tern plugin types plugin           # refresh gitignored plugin/tern.d.luau for editor types
```

Tool lookup order: env `LUAU`/`LUAU_LSP`/`TERN` → `~/.cache/plotroom-check/` (`$XDG_CACHE_HOME`) → PATH. Missing tool = failure, not skip. `PLOTROOM_BENCH_BUDGET_MS` (default 250) caps the slowest bench row. `types` fails on **any** luau-lsp diagnostic, warnings included, over `plugin/*.luau` and `plugin/tests/*.luau`.

## Code Conventions & Common Patterns

- `--!strict` at the top of every module. Modules are `local M = {}` + `function M.x`; `host`/`window` expose only registrations.
- Naming: files lowercase single word; functions/locals camelCase (`loadStore`, `kvSet`); constants SCREAMING_SNAKE (`POLL_MS`, `GH_TIMEOUT_MS`); types PascalCase, `export type` when shared; action/check ids kebab-case (`retry-checks`, `prompt-<id>`); kv keys lowercase words.
- Async is callbacks only, no coroutines. Shape: `done(value?, problem?, cx?)`. `process.run` is the only way to spawn anything.
- Errors are values: `Problem = {kind, message}`, kinds `auth|missing|rate-limit|invalid|not-found|failed|account|superseded` (`github.luau` L10-12). Wrap `tern.kv`/`tern.json` calls in `pcall`; never overwrite unreadable or malformed storage; validate untrusted input at the boundary (`validStore`, `parsePage`, size caps).
- Stale-callback guards are mandatory: check `alive(state)` and `state.gen` in host callbacks; window uses `defer` to fetch a fresh `cx`.
- Security: every command is an argv array (`{"git", "worktree", "add", ...}`); never build shell strings.
- UI: native Tern kinds only (`picker`, `prefs`, `list`/`item`, `overlay`, `kv`, `badge`, `md`, `meter`, `spinner`, `icon`…); there is no native button, so buttons are the picker's action bar (`itemActions`) or `item` rows with `hint` keycaps and `actions={click=...}`. No `ui.el` with plugin classes. Keys must be stable because window locates nodes by dotted key. Items are keyed `n<number>`; picker `layer.queue`; Settings is `layer.settings`, a `prefs` in the layer (Tern's right-docked side sheet) beside the queue picker, which plotroom.css narrows by the sheet's width. While Settings is open every key goes to Settings, but the queue still takes clicks (rows, sidebar views, action bar; a click first ends the single-line edit, as a click on another Settings row does); its Settings button closes the sheet, and Remove worktree closes it before asking.
- CSS (`plotroom.css`): only where no kind or prop covers it (a handful of rules); never restyle what a kind draws. Every selector starts with `[data-surface='plugin.plotroom.prs']`; use Tern tokens; no logical properties, `rem`/`ch`, or `:has()`.
- Deliberate shortcuts carry a `ponytail:` comment naming the ceiling and upgrade path.
- Annotate with SDK types from `tern.d.luau` (`BlockCx`, `WindowCx`, `Node`, `BlockView`, `ProcessResult`, `TimerHandle`, ...).

## Testing & QA

- No framework. `check.py test` bundles every `plugin/*.luau` and `plugin/tests/*.luau` into one temp script (each module wrapped as `function(tern, require, os)`) and runs `luau` on it. Pass = exit 0 and stdout `REGRESSION cases=N failed=0`.
- Add cases to `plugin/tests/regression.luau` with `case("module: behavior", fn)` (host context) or `windowCase(...)` (window context). Each case gets a fresh `World` (`newWorld`): fake SDK with virtual clock (`advance`/`runUntil`/`flush`), in-memory `fs`/`kv`, and `w.respond(fn)` to answer `process.run` spawns; unmatched spawns fail the case at `w.finish()`. Assertion helpers: `eq`, `same`, `yes`, `has`, `lacks`.

```lua
case("input: clean drops only malformed bytes and control characters", function(w: World)
	local input = w.load("input") :: Input
	eq(input.clean("é\x80b"), "éb", "stray continuation byte after a valid character")
end)
```

- Prefer behavioral assertions (rendered text, argv, kv contents, toasts). Case names are prefixed by module (`github.search:`, `worktree:`, `host:`).
- Pure helpers with no SDK dependency go in `plugin/tests/check.luau` (bare `assert`), which runs both in the bundle and in-app via the `selftest` palette command.
- No coverage tool or threshold. Bench rows (`BENCH <name> ms=…`, 1000 PRs) must stay under budget; smoke covers the real-git worktree scenarios listed in `scripts/check.py` (create, reuse, dirty reuse, advanced head, post-checkout hook, existing branch, deleted head branch, `.github`, recovery, fork PRs, folder names, issue worktree, Jira issue worktree, issue on a linked PR, remote branches, scan), the real-git worktree inventory and removal, the draft pull request preview and non-forced push (against local bare remotes behind a fake ssh), and, on real Plotroom blocks with a fake gh, triage/sort/Worktrees board, Open item by URL, export and import (Cancel writes nothing, Import does) and agent launch/jump/duplicate offer, plus a block on an attached loopback host making its worktree through the real window → host → window link flow. Smoke writes nothing to any real remote.
- Fake-SDK window cases that need the host's answers use `linkQueue`/`agentScene`, which `w.link` a real host block to the window's pane.
- A block probes `gh --version` and `acli --version` before it lists any view: `newWorld` answers both as installed unless a model (`newGh`, `newAcli`) answers first; `hx.uninstalled(w, program)` makes one fail to start until its switch's `missing` is set false.
- `newWorld` seeds kv `keys` with the classic one-key bindings (`j k w g a G m z Z n o / r s ?`), so cases drive the queue by key; a case about the real defaults (only `.`) clears it first (`w.kv.store.keys = nil :: any`). `goToSettings` opens Settings through the palette's `queue` event, needing no key.
- With no `prompts-prs`/`prompts-issues` in kv a kind offers its default prompts, which become picker rows and hidden run links: a case about an empty prompt store saves one first (`savePrompts(w, {})`, `saveIssuePrompts(w, {})`).
- The fake gh/git models (`newGh`, `newGit`) answer what worktrees ask: `gh.meta` (PR heads, `headRepo` absent = a deleted fork), `gh.linked` (an issue's linked PRs), `git.served`/`git.defaultBranch` (the remote's branches), `git.config` (what `git config` wrote). `scene`/`openWt` (PR worktrees) and `issueRepo`/`openIssuePlan` (issue worktrees) build on them.
- The fake `tern.json.array` and decoded JSON arrays carry a protected metatable as in real Tern, so `table.clone` on them fails in tests too; copy with a loop. `cx:frame` ops are recorded in `w.frames` (`caretOf(w)` reads the last `focus` op).
- Before finishing any change: `python3 scripts/check.py` (or `--ci` without Tern) must pass clean.

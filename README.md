# ⎇ Tern Plotroom

**Your pull requests and issues, in one block inside [Tern](https://docs.stencil.so/tern).**
Triage with the keyboard. One key checks a PR or issue out into its own worktree. Another points an agent at it.

## Install

Requires Tern 0.9.8, `git` ≥ 2.36 and [`omp`](https://github.com/can1357/oh-my-pi) (worktrees and agents), plus the CLI of each integration you use: `gh` signed in to github.com for GitHub, Atlassian's [`acli`](https://developer.atlassian.com/cloud/acli) signed in (`acli jira auth login`) for Jira. An integration is only there while its CLI is installed on the block's host: without `gh`, Plotroom has no GitHub views, groups or prompts, only Settings › GitHub with a **Setup guide** button to gh's install instructions; without `acli`, the same for Jira (Settings › Jira). Install the CLI, then Refresh (or show its setup page again) and the integration turns on.

```sh
tern plugin install github.com/andyhite/tern-plotroom/plugin
```

Then, from any pane: palette → **Plotroom: Open**. One Plotroom block holds every saved view in its sidebar: GitHub pull requests and issues, and Jira issues. Opened inside a github.com checkout, it saves that checkout as the one its worktrees come from (Settings › Repositories).

The Files pane's **Open Plotroom** header button opens the same block beside the focused pane, starting in the folder Files shows. If that folder belongs to another host, focus a pane on that host first; Plotroom never interprets one host's path on another.

Update later with the same command plus `--force`.

**From the separate Issues block.** There is no *Plotroom: Open Issues* command any more: Plotroom: Open is the one entry point and shows issue views too. Tern has no way to convert a pane, so a pane of the old Issues block does not work in the new version: close it and open Plotroom once. A pane of the old PR block reopens as it was. Your saved views and prompts are not touched: the new block reads them where they are.

**Remote hosts.** A Plotroom pane on a remote host works like a local one: the queue, worktrees and agents run on that host, with its `gh`, `git`, `omp`, checkouts and saved settings. Install the same Plotroom version on both machines (the command above, run on each); plugins are not updated or synchronized automatically. The plugin's version tracks its protocol (`0.<protocol>.0`), so `tern plugin list` on each host tells whether the two builds speak the same one. With Tern's status bar enabled, a focused Plotroom pane shows **Plotroom protocol mismatch** when its host announces a different protocol. The local window checks on focus and every two seconds while Plotroom stays focused, so the warning clears when the protocols match. A missing marker while the block loads shows no warning. This checks compatibility, not whether two builds have the same release or commit; host-backed actions still refuse an incompatible or missing protocol.

## What it does

| | |
| --- | --- |
| 🔍 **Typed views** | Saved searches in one sidebar, each a **Pull requests** or an **Issues** view. A GitHub view takes a GitHub search query across every repository its login can see (`repo:`, `org:` and `user:` narrow it); a Jira view takes JQL across every project `acli` can see. The sidebar groups the GitHub pull request and issue views together, with Jira views alongside. In a block 127 columns wide or narrower the sidebar folds into a dropdown whose entries read `GitHub - octocat: My PRs` (integration, profile when there is one, then the view) and show no counts. Settings › Views has a group for each `gh` login signed in and one for Jira while `acli` is installed, each with its views and an **Add view** button: the new view searches as that login (or through Jira) and is of the active view's type, an Issues view for Jira. While a group lacks one of the default views, **Restore defaults** beside Add view adds back each default it has none named like, as that group's (an edited default keeps your query). A view's form holds its Type (GitHub views), name, query, grouping and prompts. Changing a view's Type keeps its name and query but not the prompts offered under it. Issue views list In Progress, then To Do, then Done. |
| 🧭 **Default views** | A first run starts with these. Pull requests: **My PRs** (grouped by repository) and **Review requested** (asked of you directly, oldest waiting first, without drafts). GitHub issues: **Assigned to me** and **Created by me** (assigned to someone else or no one). All GitHub defaults skip archived repositories; those not marked otherwise are grouped by repository. Jira: **My sprint** (yours, by status) and **Up for grabs** (unassigned, not started), both in an open sprint; **My epics** (by status). Only My epics lists epics (`hierarchyLevel = 1`); the others take `hierarchyLevel < 1`, whatever your site calls its epic type. The two sprint views come only when the Jira site has sprints: Plotroom asks once `acli` starts (again on Refresh), and Restore defaults offers them once it does. Settings › Views › Restore defaults adds back any default an existing install is missing. |
| ⚡ **Polite refresh** | Every 60 s while quota is ample; backs off from GitHub's rate-limit headers instead of hammering. |
| ✅ **Checks and details** | The selected PR's full check list, re-runs collapsed to the newest, with its merge state (conflicts, behind base, blocked, ready), each reviewer's latest verdict and who is still requested, and its description folded above the facts. Reloaded on every successful refresh, so check status changes show up even when the PR itself is unchanged. Linked pull requests and issues (an issue's linked PRs, a PR's closing issues, a Jira issue's links) show as their own sections with state and a short excerpt of the description; a link Plotroom cannot read falls back to its name (the file's basename for a path) instead of an error. |
| 🔀 **Merge and review** | From the command palette's GitHub - PR group: **Merge…** (the methods the repository allows, plus **Auto-merge when checks pass** while checks are pending; bound to the planned head commit, so a later push refuses it; never deletes the branch, never uses admin override), **Approve…** (optional comment), **Request changes…** (comment required) and **Update branch…** (only while the PR is behind its base; GitHub's default merge update). Each is confirmed first, naming the PR and the `gh` account. |
| 🌳 **Worktrees** | **Worktree** checks the PR out on its own head branch with `omp worktree add` into omp's worktree directory (default `~/.omp/wt`) as `plotroom-<owner>_<repo>-pr-N` (the folder name format is yours to change), and opens a tab there. On an issue, it uses the issue's linked pull request's branch, else a new branch from a base you pick. Never resets or cleans anything of yours; the preview's worktree card can remove the worktree, asking first and never forcing it. Needs the repository's local checkout (Settings › Repositories); without one, Worktree, agents and prompts ask for it. |
| 🤖 **Agents** | The command palette's **Saved actions** group: pick a saved action (Settings › Actions) offered under the current view, or **Type a prompt…**, and it starts an [omp](https://github.com/can1357/oh-my-pi) agent block (Tern's `cx.agents:start`) inside the item's worktree (or, as the action says, the repository's main checkout) with that prompt, no questions asked. An action may name the model omp runs it with (`omp --model`): a role alias such as `@slow`, or a model such as `opus`. Give an action a key (Settings › Keyboard shortcuts) to run it straight from the queue. |
| 🔗 **Linked PRs** | On an issue, click a linked pull request to show it in the same block: it is selected in the active view when that lists pull requests and has it; otherwise it is looked up alone under an `owner/name#N` entry at the top of the sidebar, and the other views stay there to go back to. |
| 📥 **Inbox** | The last list in the sidebar shows what GitHub's notifications say needs you: unread threads you take part in (review requested, mention, assigned, CI…), grouped by repository, each with its reason and the pull request or issue it is about. **Enter** shows that item in the block as a linked pull request is; **Mark read…** (command palette) marks the listed threads read after one confirmation. Read as `gh`'s active login only. |
| 🐚 **Shell lens** | After `gh pr create` in a shell pane, a lens shows the new pull request's URL with **Show in Plotroom**, **Copy** and **Open in browser**. Show in Plotroom opens it in a Plotroom block on that shell's host, as Open item by URL does (fetched, then pinned), launching Plotroom first when none is open; the lens runs nothing else. Output with no pull request URL (a failed or cancelled create) stays raw, and Tern never lenses pipelines or redirects. |
| 👤 **Per-view accounts** | Work and personal `gh` logins on one machine: each signed-in login has its own group of views in the sidebar, searching as that login. Tokens stay in memory, never on disk. |

## Keys and the command palette

`.` opens the **command palette**, the one key bound by default. Its rows are grouped and filtered to what applies now, **Saved actions** first (Type a prompt…, the actions offered under the view, and Go to agent while the item has one, plus Interrupt agent, Stop agent… and Message agent… while its agent is live; there is no Agent picker in the menu), then **Jira - Issue**, **GitHub - PR** and **GitHub - Issue** (the selected item's own operations, under the heading of its type: Open in GitHub or Jira, Worktree, Go to tab while the item has a tab, Assign to me, Comment…, Add or Remove label…, Close or Reopen issue…, Ready for review… or Convert to draft…, Merge…, Approve…, Request changes…, Update branch… while the preview shows the branch behind its base, Jira transition…, Re-run failed checks, Re-run all jobs…, Cancel running workflow…, Draft PR…, each only where it applies), **Inbox** (Mark read… while the Inbox lists notifications), **Triage** (Mark seen, Snooze, Unpin while it is pinned), **Filter & Sort** (Show or hide snoozed, Needs attention only, Next sort order, Search, Refresh), **Views** (every sidebar scope in the sidebar's order, Pins, the Worktrees, Agents and Inbox lists included, and Open item by URL…) and **Configuration** (Settings, Shortcut list, Export and Import). Rows that need a selection are not listed without one, nor are commands the item cannot take (no Jira transition on a GitHub issue, no re-run without a matching run); each row shows its key if it has one. Settings › Keyboard shortcuts gives any queue action, and any saved action, a key of its own (Enter on its row, then the key, or Backspace to remove it), for pull requests and issues alike and per machine. The action bar at the bottom of the queue shows only the buttons that have a key (the Worktrees list's Remove finished button needs none) (an error card with no list also shows Refresh and Settings); the preview's head opens the item in GitHub or Jira (the globe icon). The arrows, `Enter` (open the item in a Browser block beside the queue), `Tab` (views ↔ list), `Esc`, Page Up/Down, Home and End are fixed. **A view with items selects its first item when it opens** (the Worktrees list, its first worktree), so a preview always shows; it cannot be closed. `Esc` clears a search, moves focus from the sidebar back to the list and cancels the dialog it applies to; it never clears the selection. A selected item's preview stays usable in a narrow block, shown below the list. Once bound, `?`'s Shortcut list shows the keys as you have set them. Settings › Keyboard shortcuts has a **Use one-key shortcuts** row that binds the classic set (`j`/`k` move, `w` worktree, `g` go to tab, `a` agent picker, `G` go to agent, `m` mark seen, `z`/`Z` snooze, `n` attention, `o` sort, `/` search, `r` refresh, `s` settings, `?` help, `u` find finished worktrees, `d` remove) to the actions that have no key; a key you saved keeps its action (a shortcut you removed stays removed), and a preset key another action or saved action already uses is skipped and listed in a toast.

The palette lists only names, details and keys: a saved action's prompt text is not sent with it (the action runs through its own link, which fetches the text), so many or long prompts never push rows out of the palette. Opened from the **Agents list**, it offers **Go to agent**, **Interrupt agent**, **Stop agent…** and **Message agent…** for the selected row (its own **Agents** group), the views, Settings and the shortcut list, and none of the queue's Snooze, attention, sort, search or Refresh rows.
Starting an action by its key, a palette row or a typed prompt while a live agent already works on the item first asks **Go to agent (state)** or **Start <action> anyway**; Cancel starts nothing. The Agent picker lists every action whatever the size of their texts, and a pick fetches its own text.


A saved action's own key wins over Go to agent, Mark seen, Snooze, Show or hide snoozed, Needs attention only, Next sort order and the command palette while that action is offered for the selected item: it was that key first. Likewise a key you saved for any queue action is yours first: the palette's default `.` is left unbound when you gave `.` to something else. Imports never take a key the queue already uses.

The palette's item rows also offer **Copy link**, **Copy number** (`#N`, or the Jira key) and, when the item has a head branch or a worktree branch, **Copy branch**. The pane title adds how many items need attention (new or changed, not snoozed, or with an agent waiting) when that isn't zero: `Plotroom · My PRs (12) · 3 new`.

## Triage, agents and commands

- **Seen is automatic; snooze is local.** Each item shows **New** (never seen) or **Changed** (its state, title, review, checks, head, comments, labels or assignees differ from when it was last seen). An item is marked seen when it is selected and its preview is shown, and again if a refresh changes it while it stays shown; a background fetch and the Worktrees list never mark anything. **Mark seen** stays in the palette to do it by hand. Under **Needs attention only** the selected row stays listed, though reading it marked it seen, until the selection moves. **Snooze** holds an item until 08:00 local time on the next calendar day, even when it is still early morning (a **Snoozed** badge when listed with **Show or hide snoozed**). **Needs attention only** keeps only items that need attention: unseen, changed and not snoozed, or whose agent waits for input. An agent waiting for input surfaces its item even when snoozed. Seen and snooze state is per machine (kv `triage`) and cannot be shared by export.
- **Filters survive a restart.** **Needs attention only** and **Show or hide snoozed** are saved with the pane and come back with it.
- **Agent states are not results.** A row's badge is the state of the agent pane started from it: Working, Needs input, Idle or Exited. Only Needs input asks for you; Idle and Exited do not mean the work succeeded. **Go to agent** (palette, or `Plotroom: Go to the selected item's agent`) focuses exactly that pane. While the selected item's agent (or the selected Agents row) is live, the palette also offers **Interrupt agent** (Ctrl-C to its current turn; the agent stays open), **Message agent…** (asks for one line and sends it) and **Stop agent…** (asks first, Cancel being the first row, then closes the agent's block and ends its program). An exited agent, a blank message or a message the agent cannot take now only shows a toast and changes nothing. The link is remembered per host: it counts only for a Plotroom block on the machine that started the agent, so a remote block never jumps to a local agent's pane.
- **Agents that need input.** With Tern's status bar enabled, every pane's status line shows **N agents need input** while any agent in the Agents list of an open Plotroom block is waiting; clicking it (or `Plotroom: Go to the first agent that needs input`) focuses the first waiting agent's pane, as Go to agent does. Each agent that starts waiting also gets one toast naming its item and action. Tern's agent-state events schedule an update on the next turn of the UI event loop, without waiting for the four-second reconciliation timer. Tern's own Settings › Agents › Notifications controls system notifications; Plotroom does not add a second system-notification channel.
- **Items that need attention.** With Tern's status bar enabled, the status line also shows **N need attention**: the items needing attention, summed over every open Plotroom block (checked every 4 seconds, hidden at zero).
- **Worktree tabs are named after their item.** A tab opened at a Plotroom worktree is titled `#123 title` (or `KEY-1 summary` for Jira) unless you renamed it. The names are kept in memory only, so after a plugin reload the tab shows its plain name.
- **Sorting.** **Next sort order** cycles the active view through its sorts and saves it with the view (Settings › Views › Sort by, or Default order); the left side of the bottom command bar shows the current `Sort: …` (the saved sort, else the default), together with Needs attention only when it is on. GitHub pull requests: Recently updated, Oldest waiting (by creation time), Review required first, Largest changes first (additions plus deletions). GitHub issues: Recently updated, Oldest waiting (by creation time). Jira issues: Priority (Jira lists keep no update time), always within status category: In Progress, then To Do, then Done (shown only when the filter includes it), whatever the sort; `Status` groups follow the same order, by status name within a category. A group's items are sorted inside it. Pinned items have no sort. Changing a GitHub view's Type keeps its sort where the new type offers it; otherwise the view returns to default order and a toast says so. Settings › Views › Group by also offers Fork (pull requests: the fork's owner, else Same repository) and Label (the item's first label, else No label; GitHub and Jira). A search that matches nothing says so with its text; the preview of a snoozed item has an Unsnooze row; a worktree removal git refused offers only Keep.
- **The Agents list** (in the sidebar after the Worktrees list, before the Inbox) shows your live agents: those that are Working, Need input or are Idle, grouped by repository, each row with the item's title, the action's name, the branch, the agent's last message (cut to 200 bytes), why its last prompt was not delivered when it was not, and the state badge; the preview shows the same. When an agent's turn ends, how it ended (done, failed, exited or closed) and the time are saved with its link and shown on the row ("Review: done 14:02"). Exited agents are hidden, and the sidebar counts the rest. Enter (or a click, or **Go to agent**) goes to the selected agent's tab, for a GitHub item or a Jira issue alike. State changes update from Tern's events; a four-second reconciliation reads Tern's agent list for last messages, delivery errors and recovery after a reload. Neither path queries GitHub or Jira, and no view has to be loaded. The action, branch and title are saved with the agent's link when the agent starts, so an agent started before that shows no action, branch or title (just its item key and state), but still shows Tern's last message and any delivery error, and a result once its next turn ends.
- **The Inbox list** (last in the sidebar) shows the unread GitHub notifications that `gh`'s active login takes part in (`notifications?participating=true`, the first 50), grouped by repository, each with its reason (Review requested, Mention, CI…) and the pull request or issue it is about. Enter shows that item in the block as a linked pull request is (selected in place when the shown view lists it, else pinned); a thread about neither, such as a CI run, says so. It is read when opened and then with the queue's refresh, but GitHub's `X-Poll-Interval` is obeyed (no request is sent sooner) and the read is conditional on `Last-Modified`, so an unchanged inbox (304) costs no quota and keeps the rows. **Mark read…** (command palette, while notifications are listed) confirms with Cancel first, naming the account and how many threads per repository, then marks exactly those threads read: read, never done, so GitHub keeps them in its inbox. The account is fixed when the plan is made. Without `gh`, or when the login's token cannot read notifications, the list shows the problem and the fix (`gh auth refresh -h github.com -s notifications`); it never falls back to another login.
- **Item commands** (the command palette, or Tern's palette's `Plotroom:` entries) change things on GitHub or Jira only after a confirmation that names the item and account and lists what will be sent; its first row is Cancel. A comment's full text is shown in the confirmation, and a Jira comment's confirmation is bound to the Jira account's email and site as read at that moment; a comment that cannot fit the confirmation in full is refused rather than sent partly unseen. The GitHub account is fixed when the plan is made, so a later account switch cannot redirect a confirmed command. They are: assign a GitHub or Jira issue to you, comment on a GitHub or Jira item, add or remove a GitHub issue's label, close or reopen a GitHub issue (GitHub's default close reason), mark a draft pull request ready for review or convert one to a draft, merge, approve, request changes on or update the branch of a pull request, move a Jira issue through one of its transitions, and three CI commands. **Merge…** offers the methods the repository allows (squash, merge commit, rebase), plus **Auto-merge when checks pass** while checks are pending; the merge is bound to the head commit shown in the confirmation (`--match-head-commit`), so a push after planning refuses it (auto-merge checks the head only when it is enabled, and GitHub then merges a later push by anyone with write access once checks pass; it is not offered, and refused, while the pull request can already merge, as `gh` would merge it at once); it never deletes the branch (a worktree may sit on it) and never uses admin override. **Request changes…** needs a comment and **Approve…** takes an optional one; each is shown in full in the confirmation and refused when it cannot fit, like comments. **Update branch…** is offered only while the preview shows the branch behind its base and uses GitHub's default merge update. **Re-run failed checks** lists every failed GitHub Actions workflow run of the pull request in a picker and re-runs only the failed jobs of the one you select; **Re-run all jobs…** re-runs every job of a finished run you select; **Cancel running workflow…** cancels the active run you select. Checks without an Actions run are not touched.
- **The palette's Jira transition… picker needs an API token.** Listing and applying transitions uses Jira's REST API, which `acli` cannot do (it cannot list a work item's transitions). Create a standard Jira API token (id.atlassian.com › Security › API tokens), export it as `PLOTROOM_JIRA_API_TOKEN` in the environment Tern starts from **on the host the block runs on**, and restart Tern. Plotroom reads it per call, never stores or logs it and never puts it in a command line. It uses the site and email `acli` is signed in with, and first asks Jira `/myself` who the token belongs to (that request is authenticated with the token): if it is not the `acli` account, no transition is applied. Without the token, the picker explains this; assigning a Jira issue to you and an action's Move to status keep using `acli` and need no token.
- **Draft pull request** (issue with a Plotroom worktree). Pick the GitHub repository (every distinct GitHub remote of the checkout) and then a base branch (remote default first); every step checks the repository is still one of them. The preview shows the title, description, `branch → base`, the commits, whether the branch must be pushed and that uncommitted changes stay out. Edit the title or description (the description prompt is one line and replaces all of it; Esc while editing returns to the previous review, it does not abort), then confirm. Before anything is sent the branch, its head and the base are read again; if they moved, or if whether it needs pushing changed, nothing is pushed or created. Otherwise the branch is pushed if needed (never forced, nothing is committed) and a **draft** pull request is created as the view's account.
- **Open item by URL** (palette): a GitHub pull request or issue URL, or a Jira issue URL. It is fetched first, so a missing or unreachable item is reported, then shown in the sidebar's **Pins** group, even when a listed view already holds it; nothing opens in a browser. Pins accumulate (up to 20; one more is refused with a toast) instead of replacing each other; **Unpin** (preview or palette) removes one and leaves the rest. Pins are saved with the pane, so reopening Plotroom refetches and shows them again.
- **Pasting a URL**: paste into the queue (outside the search box) and the first GitHub pull request or issue URL, or Jira issue URL, in the text opens exactly as Open item by URL does (fetched, then pinned), the outcome a toast. Text with no such URL toasts and changes nothing. While the search box is open, a paste edits the search.
- **Export and import** (palette) move saved views and actions between machines; they change only Plotroom's own saved views and actions, never GitHub or Jira. Export picks what to include, then shows the counts and any notes (actions left out, what is not included) with Cancel first; nothing is copied or written until you choose. You then pick **Copy to the clipboard** or **Write to a file…** (a path on the block's host, a new file only); each does only that. The confirmed export is exactly the snapshot you were shown, even if settings change meanwhile. A large export is file-only, to stay within the limit for passing it back to the window; the importer accepts up to 60000 bytes. An action's shortcut may be any single visible character, `é` included, by the same rule as Settings; import keeps it unless the queue already uses that key. An action name is at most 120 characters (Settings refuses a longer one, export leaves it out with a note), and import leaves out an action whose model omp would not take, with a note. It holds names, queries, groups, sorts and action text, keys, model and placement. It has no field for checkout paths, setup commands, tokens or logins: accounts leave as anonymous slots (`account-1`). An action whose text matches a few credential patterns (GitHub and AWS tokens, bearer tokens, private-key headers, `password=` followed by a literal) is left out with a note; that check cannot catch every secret, so read action text before sharing a file. Import takes pasted JSON or a file path on the block's host and previews what the file holds, including shortcut removals, account slots to map and what will be skipped, and writes nothing until you confirm; if everything ends up skipped it says so and changes nothing. More than 150 entries at once are refused before the preview (a file holds at most 100 views and 100 actions). A same-name item can be skipped, replaced or duplicated (an identical one skipped or duplicated); each account slot is mapped to a signed-in login, gh's active account, or skipped views; an action shortcut that a queue key or another action holds is removed. Both stores are read again when it writes.
- **Temporary page previews.** **Open floating preview** opens the selected item's page in Tern's native picture-in-picture Browser over Plotroom. The queue stays in its original split; closing the preview leaves that layout intact. The existing Open action still opens beside it. Use Tern's native Browser profile controls to choose shared, repository, session, named or private profiles in the Browser's address-bar chip. Browser logins are separate from the `gh` account a view searches as; Plotroom never copies CLI credentials into a browser profile or preloads hidden pages.
- **Send selected text to an agent.** Select text, then run **Plotroom: Message an agent with the selection…** from Tern's palette. Choose a live Plotroom-linked agent and review the quoted text before choosing **Send**. **Add a note…** adds an editable one-line instruction; Cancel or Escape sends nothing. File selections use the local editor's live buffer, including unsaved edits, and refuse a changed selection; remote file selections are refused rather than read from a same-named local file. Long context is explicitly clipped in the review, and only the reviewed text is sent.
- **Send a page element to an agent.** With an item or Agents row selected, run **Send a Browser page element to the selected item's agent…**. Choose an already-open Browser when there is more than one, then click an element (Escape cancels). The review contains its page, selector and text, never its form-field value. Add a note if needed and explicitly choose Send. The page stays in its existing browser profile. Tern 0.9.8's browser driver cannot inspect Browser blocks on remote hosts: picking from one reports an error and sends nothing. Floating previews themselves work on local and remote panes.
- **Paused plugin hooks.** If Tern temporarily pauses a Plotroom hook for exceeding its execution budget, Plotroom shows a toast and status-bar notice. Tern resumes it automatically; Plotroom then reconciles agent status. The notice is not a GitHub rate-limit warning.

## Worktrees

```mermaid
flowchart LR
    W([w]) --> E{exists?}
    E -- yes --> R[reuse as-is] --> T[open tab]
    E -- "no, PR" --> F[fetch the PR head] --> C[omp worktree add on its branch] --> S[your setup commands] --> T
    E -- "no, issue" --> L{linked PR with a live branch?}
    L -- "one (or the one you pick)" --> F
    L -- "none (or New branch…)" --> B[pick a base, fetch it] --> N[new branch from the format] --> C
```

- **The Worktrees list** (after the views in the sidebar) lists every worktree of every saved checkout straight from git, whatever the current query: branch, path and badges (Main, In tab, Changes, Clean or Unknown, Merged/Closed, Locked, Missing, Unnoted). **Changes** (uncommitted changes) and **Clean** are read automatically while the view is shown, with no key to press: the selected row first, then up to 40 worktrees per scan, rotating through the rest, and a scan is due again 30 s after the last one started. **Unknown** means git could not read the changes there; a row not read yet says Reading…. `Enter` opens one in a tab, **Find finished worktrees** asks GitHub or Jira whether the items of up to 20 worktrees per press are merged or closed (a badge only, nothing is removed), **Remove worktree** asks and then `d` removes (Enter or Esc keeps it), **Remove finished worktrees** lists every row Find finished worktrees marked Merged or Closed (never an unchecked, main, locked or missing one; the confirm says how many weren't checked) and asks once: `d` removes them all one at a time, Enter or Esc keeps them; a worktree with changes is refused and kept, and the toast counts removed and kept rows. It is refused while another board operation runs. All three are in the command palette; Find and Remove worktree can be bound in Settings › Keyboard shortcuts to get a key and a footer button. Removal is never forced and refuses the main worktree, a locked or missing one and one with uncommitted changes. Only a branch Plotroom noted for a pull request or issue (kept in the checkout's own git config) is deleted with its worktree, and then like Remove worktree below; a worktree marked Unnoted keeps its branch. At most 200 rows and 50 checkouts are read.
- Worktrees go in omp's worktree directory: `OMP_WORKTREE_DIR`, else omp's `worktree.base` setting, else `~/.omp/wt` (trailing and doubled slashes dropped, so it matches git's own listing); Plotroom has no folder setting of its own. The repository's saved checkout (Settings › Repositories; opening Plotroom inside a checkout, or a linked worktree of it, saves its main checkout) is only where the worktree is added from.
- **Setting a checkout** (Settings › Repositories, or the prompt Worktree, agents and actions open when a repository has none) verifies the folder and clones into a new or empty one with `gh repo clone`, which can take minutes. One repository is set up one at a time across every pane: a second attempt meanwhile is refused as busy, and its row is disabled. If the repository was removed, cleared or given another checkout while it cloned, the finished clone is not saved (Settings shows "Checkout not saved"), and a clone that ends after its block closed saves nothing. A clone that fails never disturbs a field you are typing in.
- A pull request's worktree is on its own head branch, tracking it on GitHub (a fork's as `<fork owner>/<branch>`, tracking the fork), so `git pull`, `git push` and `gh pr view` work inside it without arguments. A fork PR's local branch is named differently from the fork's, so push with `git push <fork remote> HEAD:<branch>` (the fork's URL or a remote you added for it). A local branch of that name that already exists is used as it is, never moved; one that is noted for another pull request (a same-repository head `alice/x` against alice's fork branch `x`) is refused, naming both PRs. A worktree an earlier version made at the PR's folder (on `plotroom/<owner>/<repo>/pr-N`) is still reused.
- An issue's worktree is on the branch of its linked pull request when exactly one same-repository one still has its branch on GitHub; with several, or when only a fork's is left, Plotroom asks which, or a New branch, and fetches nothing until you pick. A fork's pull request (a deleted fork's counts, owned by its author) is never checked out unasked, and shows in that choice marked with its owner. A merged pull request is never linked: its branch is spent, so new work on it would never reach the base. A GitHub issue's linked PRs are those that close it; a Jira issue's are the pull requests of its repository whose title or head branch names its key. A new branch asks for the base branch it starts from (the remote's default first), fetches that base, and is named by the branch format. GitHub logins may contain `_` (Enterprise Managed Users), and a Jira repository typed as anything but `owner/name` is refused with a message.
- **Name formats** (Settings › Worktrees): the new issue branch (default `{github.user}/{key}-{slug}`; a repository can have its own, under Settings › Repositories) and the folder names of PR and issue worktrees (defaults `plotroom-{owner}_{repo}-pr-{key}` and `plotroom-{owner}_{repo}-issue-{key}`, where `{owner}` and `{repo}` are lowercase). A branch format takes `{key}` `{slug}` `{owner}` `{repo}` `{project}` `{github.user}` `{jira.user}`; a folder format takes `{key}` `{slug}` `{owner}` `{repo}` and no `/`. Both need `{key}`. `{github.user}` is the view's `gh` account, else `gh`'s active one; `{jira.user}` is your Jira sign-in's email before the `@`.
- Reused worktrees are never updated. The preview's worktree card shows `Up to date|Not at PR head` and `Clean|Uncommitted changes|Changes unchecked` badges (their tooltip is the one-line summary), its branch and path, and, when the worktree is not at the PR's head, the `git pull --ff-only` command for you to run. A `N unpushed` badge says how many commits the branch holds that its upstream lacks (read with the same `git status --porcelain=v2 --branch` spawn as the changes; a branch with no upstream, such as a fork PR's worktree, shows none), and any `git …` command that finishes in a pane inside a worktree reads the card again, so the badges follow `git commit` or `git pull` at once. Its buttons: **Go to tab** while a tab works in it (else **Open in new tab**), **Remove worktree**, and **Open in Git**, which opens Tern's git block on the worktree (also a palette command, on the card and on a Worktrees list row). It shows while the worktree's folder exists and works for a block on this machine only: a block on a remote host is refused.
- **The card is read from git, not remembered.** After every refresh, Worktree press and removal (and when a checkout is saved) Plotroom lists the saved checkouts of the repositories on screen with `git worktree list`; it never asks per row. A worktree is a PR's when it is on the PR's head branch or in the folder the PR folder format names (every item that names it has it, e.g. an issue and its PR on one branch); an issue's when it is on the branch or in the folder the issue formats name now. So a block opened later, or after a plugin reload, shows the card and the row's **Worktree** badge of every such worktree, with no Worktree press; one you removed yourself leaves at the next refresh; and a read that fails changes nothing. `Up to date` compares the worktree's HEAD with the PR head the last refresh saw (a PR pushed since reads as it was until the next refresh). `Clean` / `Uncommitted changes` is read with `git status` for the selected PR only, once the cursor rests on it and again after each refresh; until then the badge says `Changes unchecked` and the row's badge has no colour.
- **The preview shows both halves of a worktree.** On an issue whose worktree's branch is the head of a GitHub pull request in the code repository (`gh pr list --head <branch> --state all`; an open one wins), a **Pull request** section shows it (number, title, state, a link that shows it in this block), unless the issue's linked list already has it. On a pull request whose head branch (a fork's as `<owner>/<branch>`) is the branch of a worktree the last scan noted for an issue, an **Issue** section shows its key, title and status, linking to it; it is read as the view's GitHub account, and the first of two issues on one branch wins. The scan notes an issue's worktree only once an issue list has been shown, so before that the pull request preview has no Issue section; the next refresh's scan fills it. The Worktrees list does the same for a row with an issue and no pull request: the pull request on its branch shows as the row's Pull request. These lookups ride the preview's own detail load (after the cursor rests; nothing polls), are best effort (a failed one shows nothing) and are read again on a refresh.
- **Remove worktree** asks first (`d` or Remove removes it; Enter or Esc keeps it) and runs on the host that has the checkout, by the same path as the Worktrees list: it re-reads `git worktree list` for the worktree and its branch first, then runs `git worktree remove` without `--force`, so git (run with `LC_ALL=C`, so its refusal is read in any language) refuses a worktree with uncommitted changes and the card says why. Then its branch, and the confirm (read from git when it opens) says which case applies: a branch Plotroom noted for a pull request or issue goes only if git confirms nothing is lost, an unnoted or guessed one is kept, and a detached worktree has none. A pull request's goes with `branch -D` only when `git merge-base --is-ancestor refs/heads/<branch>` (never a short name, which a same-named tag would win) finds every commit of it in the ref fetched for the PR (and that ref goes too), else with `branch -d`; an issue's goes with `branch -d`. A branch git keeps stays, with its ref, and the toast names it. Plotroom never runs `reset`, `clean`, `stash` or `prune`.
- **Setup commands** (Settings › Repositories) run in the new tab's shell when a worktree is *created*. They execute the PR's code (`pnpm install` runs its scripts), so leave them empty for repos that take untrusted PRs. A **fork** PR's new worktree never runs them (the toast says "setup skipped: fork PR"), and its checkout runs with git hooks off (`core.hooksPath=/dev/null`); run setup there yourself once you trust the code.
- **Actions** (Settings › Actions) become rows in the command palette's Saved actions group. Pull requests and issues each keep their own actions; the page lists both. Each has a name, a multi-line prompt (Edit… opens an editor; Enter is a new line, ⌘↵ saves, Esc cancels), and the views it is offered under; with none turned on it is offered under every view of its type. In a PR action's prompt, or a typed one, `{url}`, `{owner}`, `{repo}`, `{number}`, `{title}`, `{author}`, `{branch}` (the PR's head branch), `{base}` (the branch it merges into), `{remote}` (the checkout's git remote of the repository) and `{github.user}` (your GitHub login) become the PR's details, read fresh from GitHub; an issue's actions also take `{jira.user}`, and in a worktree `{base}` (the base a new branch was made from; empty when Plotroom reused a branch) and `{remote}`. Any other `{…}` stays as written. Actions are saved per machine, like views; Settings › Keyboard shortcuts lists each one too, to give it a key (not one the queue uses).
- **Default actions**: until you change a kind's actions, pull requests offer **Review** (an evidence-based review, posted only as you authorize), **Quick review** (the same review by reading only: no tests, builds or checks; runs in the main checkout), **Address feedback** (a fix-and-reply plan you approve before anything is pushed or posted) and **Watch** (keeps your own PR green until it merges, escalating what it may not decide), and issues offer **Implement** (features and tasks), **Fix** (bugs: reproduce, root cause, regression test) and **Plan** (an epic broken into tickets, filed as you approve; runs in the main checkout). They are written for omp in Plotroom's worktrees: they act as `{github.user}` through `gh auth token --user`, use `acli` for Jira, ask through omp's `ask` tool, and push or post nothing without your explicit answer. The first change on the page (an edit, a new action, a delete) saves them as yours. **Restore defaults**, shown while a kind lacks one, adds back each default no saved action is named like; an edited default keeps your text (delete it, then restore, to get the original back).
- **Action models**: an action's Model (empty: omp's default) starts its agent as `omp --model <model>`. Anything `omp --model` takes works: a role alias from your omp config (`@slow`, `@smol`, `@plan`), a fuzzy pattern (`opus`) or `provider/model-id`.
- **Move to status** (issue actions): an issue action's Move to status (empty: leave it) moves a Jira issue to that status when its agent starts, with no confirm; a toast reports it. It runs `acli jira workitem transition --key <key> --status <status> --yes`, so it needs no API token (that is only for the palette's Jira transition… picker). An issue already in that status (compared case-insensitively) is left alone. A status acli does not know, a transition that needs fields, or any other acli failure is an error toast with acli's message; the agent runs regardless. GitHub issues and pull request actions never move anything. Export and import carry the status.
- **Where an action runs**: an action's Runs in is Worktree by default: the item's worktree, made first if needed. Pick Main checkout for actions that need no checkout of the item's branch (review a PR, break an epic into tickets): the agent starts in the repository's main checkout, with no worktree made and no setup commands. The prompt's variables are filled in either way, except `{remote}` and an issue's `{branch}` and `{base}`.
- **Where its agent opens**: by default in a New tab (the worktree's open tab, when there is one). Set an action's Opens in to Beside the queue to open the agent as a block beside the queue, in the queue's tab; a new worktree's setup commands still run in their own tab.
- **Tell Carly when it finishes**: an action's toggle (Settings › Actions, off by default) has the started agent schedule one message to [Carly](https://tern.sh) for the end of its turn (done, failed, exited or closed). It is a fixed template naming the action and the item key, and pointing at `plotroom_agents`; no pull request or issue text and no agent output goes into it. Carly also gets a read-only `plotroom_agents` export listing the window's linked agents (item key, action name, state, and result once its turn ended); it changes nothing. Where Carly is not available the toggle does nothing and the export is not registered. A failed schedule is a toast, and the agent runs regardless. The toggle travels with Export and Import.
- **Next action**: an action's Next action (another action of the same kind, or on an issue action also a pull request action, listed by kind; none by default) starts when its agent finishes with a `done` result: the next action runs for the same item, in the same worktree, as a new pane in the tab the agent ran in (a tab of its own when that tab is gone, or the action opens beside the queue), with no confirm. A `failed`, `exited` or `closed` agent stops the chain, with a toast saying why; an agent whose turn ends while a prompt waits does not count as finished. An issue action's pull request action (Implement → Watch) runs on the open or draft pull request whose head is the issue worktree's branch in the issue's code repository, in the same worktree and tab, with the pull request's own variables only; no such pull request (none, or only merged or closed ones), a failed lookup, or an issue action that ran in the main checkout stops the chain with a toast naming why. A chained issue step reuses the code repository the chain recorded, so a Jira project mapped to several repositories is not asked about again. If the agent's host has no open Plotroom block when it finishes, a toast says to open Plotroom there and the next action is kept for the agent's next `done` finish. Pull request actions never lead to issue actions. Settings refuses a next action that would lead back to the action (A → B → A), a chain stops after 8 actions, and deleting an action clears it as anyone's next action. Export and import carry the next action along (it is exported with the actions it leads to, and dropped on import when it is missing or would close a loop). Tern has no name for a pane, so Go to agent lists each agent under the name of the action it ran.

## Trust

- No shell: `gh`, `git`, `ssh -G` and `omp` run as argv arrays. If they are not on Tern's PATH, your login shell is run to find them (its PATH is kept, and the shell is run again only when a program still cannot be started). The one exception is the agent block, which Tern starts through your login shell: Plotroom passes it `omp --model <model>` only for a model made of model-name characters (letters, digits, `@ . _ : / -`).
- Carly receives what the **Tell Carly when it finishes** toggle sends: one fixed message per run with the action's name and the item key as sent (`owner/repo#number` style, e.g. `abc#ABC-12` for a Jira key), and nothing else. Separately, wherever Carly exists it can always read the read-only `plotroom_agents` list of linked agents (item key, action name, state, result), whether or not the toggle is on. Never item titles, bodies, comments or agent output.
- Plotroom never persists integration credentials: `gh` tokens are kept in memory for up to 60 s per login (dropped at once when GitHub refuses one) and `PLOTROOM_JIRA_API_TOKEN` is read from the environment only, never saved, logged or passed as an argument. `kv.json` is plaintext and holds what you saved: views (and their sort), agent prompts, shortcut keys, checkout paths, setup commands, name formats, logins, recent agent picks, agent links (item key, agent pane, host, the action's name, branch and item title shown in the Agents list, and how the agent's last turn ended and when; never its messages) and triage memory (item key, signature hash, snooze time). Text you type into an action or a setup command is stored as typed, so keep secrets out of it.
- Every command that writes to GitHub or Jira (assign, labels, transitions, re-run, draft pull request, merge, approve, request changes, branch update, marking the Inbox's notifications read) is confirmed first, and the confirmed plan is what runs. A merge never deletes the branch and never uses admin override. The one exception is an action's Move to status, which runs without a confirm when its agent starts, because the status is your own setting on the action. Import is confirmed too, but only changes Plotroom's own saved views and actions.
- A saved account that cannot be used **fails closed**: nothing falls back to your active `gh` login.
- Agents read PR and issue text written by whoever wrote it. Be careful with agents that can act.
- Text inside a pull request or issue cannot run Plotroom actions: every action link the block renders (Open, Worktree, Go to tab, Agent, Go to agent, Interrupt, Stop and Message agent, a saved action's run, Open in Git, the Worktrees list's open) carries a random token made when the host starts, so a `plotroom://` link written into a description or comment lacks it and gets the "no longer listed" toast. The token is never shown, toasted or saved.
- A pull request whose head branch has characters outside letters, digits and `_ . / + @ -`, or does not start with a letter, digit or `_`, is refused (the message names the branch) by Worktree and agents while the queue still lists it, so a branch name never reaches git or an agent prompt as shell syntax.
- **Agents can run project code.** `omp` loads the project configuration of the directory it starts in (extensions, hooks, MCP servers), not only your setup commands. That code is trusted, not sandboxed, and Plotroom starts the agent without asking once the worktree is ready, so only run prompts on PRs whose project configuration you trust.

SSH aliases (`git@github.com-work:…`) count as GitHub when `ssh -G` resolves them to `github.com`.

<details>
<summary><b>Finer points</b> (refresh, partial results, accounts, ref names, errors)</summary>

**Refresh.** Up to 10 requests of 100 results per refresh (GitHub's 1,000 cap). Interval is 60 s with ample quota; otherwise time-to-reset is spread over 80 % of remaining requests across open panes, never under 60 s. Clicking a view in the sidebar (also the one already shown, or back from the Worktrees list) refreshes it at once, whatever the age of its last result; the timer is unchanged. A refresh already running for the view, a rate-limit cooldown and a terminal error still hold. Quota 0 or `Retry-After` pauses every automatic GitHub read (searches, head-branch lookups and the previews built on them) until reset; confirmed writes (assign, comment, labels, re-runs, draft PR) are not held, GitHub reports its own limit. A failed page discards that refresh and keeps the last complete result marked `stale`. Terminal errors (`gh` missing, not signed in, HTTP 422, `not-found`, unusable account) stop auto-refresh until you Refresh; `not-found` and 422 belong to their view, so switching to another view clears them and that view searches, while a missing or signed-out CLI holds every view. Each view keeps its last list when you switch away, shown at once while it refreshes.

**Views.** GitHub views search every repository the login can see, as GitHub search does; `repo:`, `org:` and `user:` narrow a view. Jira views are JQL over every project `acli` can see. A Jira view lists up to 1,000 items (highest priority, then newest update, first); when `acli`'s count is over 1,000 only the first 100 are listed and the view is marked partial. If `acli`'s count fails, only the first 100 are listed, and a full 100 is marked partial.

**Accounts.** A GitHub view added under a login's group in Settings › Views searches as that login: `gh auth token --user <login>` is run and the result passed as `GH_TOKEN` to each `gh` child; the token is kept in memory for up to 60 s per login, so calls within a minute share one read, and dropped as soon as GitHub refuses it. Tokens are never written to disk. The default views search as `gh`'s active login. Manage logins with `gh auth login` / `gh auth switch`.

**Refs.** Fetches land in `refs/plotroom-pr/<owner>/<repo>/pr-N` (names git refuses, such as `.github` or `a..b`, `%2E`-encoded); a same-repository head branch is also fetched into its remote-tracking ref, and a new issue branch's base into `refs/remotes/<remote>/<base>`.

**Errors you can act on.** Target directory exists but is not this item's worktree: move it. Locked or prunable record: `git worktree repair` or `prune`. A branch or folder format that cannot name one: change it in Settings › Worktrees (a repository's own branch format: Settings › Repositories). Tab did not open: run Worktree again, it reuses.

</details>
